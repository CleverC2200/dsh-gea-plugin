## 需求事实

### 目标与边界

入口为「GEA 业务版 → 计划管理 → 销售计划审批」。当前说明书描述月初 M 已有四级审批，新增纠偏 Z 审批，沿用区域、省区、大区、品类四级链及既有状态机。本期包含 Tab、列表四项业务指标、调整弹窗、保存/通过/退回动作；提报端改造和 DMS 报文变更不在本期范围，明确终审进入状态 5 才触发回写。[来源：说明书「一、背景与范围」][spec]

```mermaid
flowchart LR
  M[月初计划已终审] --> Z[纠偏提报完成且审批窗口开放]
  Z --> R[区域审批]
  R --> P[省区审批]
  P --> A[大区审批]
  A --> C[品类审批]
  C --> S5[终审通过 status 5]
  S5 --> D[DMS 追加与追减分笔回写]
  D --> S10[回写成功 status 10]
```

图示为正常通过路径；中间节点具体数字状态码及退回目标映射未在本文档完整展开，不能从图中推定。[来源：说明书「四、调整明细弹窗」§4.3、「七、测试用例」T10][spec]

### 页面与计算口径

默认月初 Tab；切换后数据源、业务指标和弹窗语境同步刷新。客户行按当前生效、未删除版本取数。四项业务指标如下，月初不展示最后一项。[来源：说明书「二、界面改造点与截图对照」§2.1、「三、列表四列」][spec]

| 指标 | 明确口径 | 理解要点 |
| --- | --- | --- |
| 月度目标金额 | `plan_doc.target_amount`，两 Tab 同源 | 同一个月初目标 |
| 月计划金额、数量 | M 生效版本的品类确认金额、数量求和 | 基准来自月初终审值 |
| 计划进度 | 当月累计发货金额/数量 ÷ 月初品类确认金额/数量 | 切换纠偏不改变分母；发货来自 `vw_v013_shipment` |
| 纠偏后进度 | 上一个已审批节点确认计划金额 ÷ 月度目标金额 | 正文定义的是调整后计划覆盖目标的比例，并非实际发货完成率 |

纠偏后进度在区域取提报端 `qty + adj_add_qty − adj_cut_qty`；省区优先取区域确认值，大区优先取省区，品类优先取大区；为空时逐级回退到提报端。正文明确 confirmed 已包含基准和调整，不能再重复叠加追加/追减。[来源：说明书「三、列表四列」上节点取值表][spec]

仅纠偏 Tab 的进度条叠加时间红线，位置为 `min(当前日, 当月天数) / 当月天数`；低于红线提示落后。顶部当前金额为月计划金额加净纠偏金额，并标注「含纠偏 ±¥Z」。[来源：说明书「三、列表四列」][spec]

### 调整语义与节点动作

弹窗下钻至客户 × SKU。基准 `qty = corr_base_qty` 为月初品类确认数量，只读。用户编辑有符号调整量；新计划量为基准加调整量，新计划金额及调整金额分别乘单价、四舍五入到两位。顶部整体差异为调整量之和，正红负绿。AI 建议本期显示「暂无真实 AI 建议」，预留 `base_qty`。[来源：说明书「四、调整明细弹窗」§4.1–4.2][spec]

默认调整按本节点 → 上游节点 → 提报端继承。正文规定编辑的是绝对调整决定，不是相比上一节点的增量：提报 +2，区域改 +8，就保存 8；省区未修改通过也写入继承的 8。由于 T4 存在冲突，下表按正文描述记录，不能视为该争议已确认。[来源：说明书 §4.1、§4.3；「七、测试用例」T2–T4][spec]

| 动作 | 数据变化 | 状态与留痕 |
| --- | --- | --- |
| 保存调整 | §4.3 明确只写本节点追加/追减，不写 confirmed | 不推进；保存日志 from=to |
| 通过 | 写本节点调整值，未改则写继承值；写 confirmed 数量与金额 | 推进到下节点；品类通过进入 5；记录本节点决定 |
| 退回 | 只清本节点 adj 和 confirmed，上下游保留 | 回到目标层级；记录原因 |
| 只读 | 非本节点审批人、节点已审或未到时无写操作 | 不改变状态 |

表据[说明书 §4.3 和「六、前端状态与边界」][spec]。退回重提另按 T7 生成 `seq+1`，提报 adj 继承上一版本、节点字段全空；它与同版本节点退回清空的规则需区分。[来源：说明书「七、测试用例」T6–T7][spec]

### 权限与边界

| 条件 | 需求行为 |
| --- | --- |
| M 未终审 | 行置灰「不可纠偏」，不允许明细/审批，后端拒绝 |
| 客户没有 Z 单 | 月计划和发货进度仍可展示；纠偏后进度为「—」，弹窗只读 |
| 非当前节点可审批身份 | 只读；提交人与当前审批人不能是同一账号 |
| 审批窗口 | 12 日提报截止后开放；具体审批区间仍待业务确认 |
| 基准加调整小于 0 | 标红「纠偏后计划数量不可为负」，保存和通过均被后端拦截 |
| 基准与调整同时为 0 | 灰显「未参与本次纠偏」，不保存；追减至 0 的行保留 |
| 同版本同节点并发 | 行锁；后写覆盖时提示刷新 |
| 所有写动作 | 写 `plan_approval_log`，可查看各节点自己的决定 |

表据[说明书「五、接口设计」通用校验、「六、前端状态与边界」、「七、测试用例」T8][spec]。

### 预期接口与验收

说明书提出列表与明细 GET、保存与审批 POST，以及 AI 建议 GET：`/plan/approval/list`、`/adjust-detail`、`/adjustment/save`、`/action`、`/ai-suggestion`（后四项同属 `/plan/approval`）。列表、明细带 `order_type=M/Z`，明细另带 `version_id`。这些是拟定契约，未证明与当前 GEA 实际接口一一对应。[来源：说明书「五、接口设计」][spec]

十项核心验收覆盖 Tab 切换、+2 改 +8 的覆盖语义、未改继承、追减、负数量阻断、退回仅清本节点、重提继承、零值行过滤、M 未终审禁止、终审与 DMS 状态联动。其中 T4 的期望有矛盾，须先修正验收依据。[来源：说明书「七、测试用例」T1–T10][spec]

## 理解推断

1. 这项功能把纠偏决定嵌入既有审批链，核心复杂度在固定基准、逐节点继承、状态推进和留痕的一致性，不能仅按新增可编辑列理解。依据为 §一、§三、§4.3。
2. 列表纠偏后进度按上节点已确认结果，弹窗按本节点草稿优先继承；依正文，保存草稿后列表指标不一定立即体现草稿值。顶部汇总是否也遵守这一时点尚不明确。依据为 §三、§4.1、§4.3。
3. 多 SKU 客户的纠偏后计划金额应逐 SKU 使用各自单价计算再合计，不能以合计数量随意乘一个单价；正文展示了逐行公式和客户聚合，但没有完整展开聚合与舍入顺序。依据为 §三、§4.1–4.2。

上述为基于[说明书相关章节][spec]的理解，尚未升级为已确认实现契约。

### 阅读中新发现的契约缺口

- 月计划金额/数量或目标金额为 0 时，比例如何展示；时间红线等于进度时如何判定，以及历史月份的时间口径未明确。来源：§三给出除法及小于/大于规则，未定义这些边界。
- 顶部「当前数量」在纠偏 Tab 的口径、净纠偏金额取本节点草稿还是上节点确认结果、按区域或品类维度是否同样改造未展开。来源：§三主要描述按客户列表和当前金额。
- 保存接口 body 已列正的追加/追减字段，但说明又要求服务端拆分正负值；缺少版本/节点的完整身份定位、零与 NULL 的继承区分及同 SKU 同时有追加追减时的约束。来源：§4.1、§五。
- 只写行锁并不能完整定义如何识别客户端旧数据；版本号、更新时间或其他冲突检测契约未给出。退回保留上下游后，重审是否允许读取旧下游决定也需和完整状态机对齐。来源：§4.3、§六。

这些缺口由[说明书相关章节][spec]对照发现，阻断相应实现和边界验收的确定性，不阻断本次功能理解。
