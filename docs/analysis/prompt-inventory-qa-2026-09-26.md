## 问题与根因

### IQ-01 / P1：选了库存 Agent，未绑页面时模型请求却归属销售 Agent

**事实**：最小 Harness 复现选中 `gea-html-inventory-fc`，真实发出的模型请求携带分仓 Persona，但 `X-GEA-Agent-Code` 为 `sales_forecast`，预期应为 `branch-inventory`。断言稳定失败。

**已确认根因**：[src/html-plugins.ts:712](/Users/synear/.codex/worktrees/gea-prompt-optimization/dsh-gea-plugin/src/html-plugins.ts:712) 的 consumerForSession 只取当前页面身份；[src/host.ts:218](/Users/synear/.codex/worktrees/gea-prompt-optimization/dsh-gea-plugin/src/host.ts:218) 在无页面时回落到默认 analysisAgentCode。工具目录则会从选中的 Agent preset 解析库存 consumer。独立查询入口已经开放，但模型和工具的身份解析没有统一。

**影响**：模型路由、Agent 侧归属和工具侧身份不一致，可能影响模型配置、审计和服务端策略；本次没有证据证明因此读到了未授权数据，也不能把其它所有答错都归因于它。

**建议**：统一 preset / 页面 / 模型 / 工具的身份解析，显式处理不一致；不能简单让所有 Agent 都用销售身份。证据：[请求归属](inventory-qa-2026-09-26/model-attribution.json)、[红灯复现](inventory-qa-2026-09-26/model-attribution.log)。

### IQ-02 / P1：两套结果截断和回读协议冲突，读完证据仍可能只是旧预览

**事实**：分仓多模型查询的证据原文共17,718字符；按 offset=0/6000/12000 续读后，内部两项 result 仍是 `resultOmitted=true` 的预览，JSON在字段中间断开。完整制品其实应沿用内部 artifact 走另一读取入口。

**已确认根因**：[src/host/agent-tools.ts:834](/Users/synear/.codex/worktrees/gea-prompt-optimization/dsh-gea-plugin/src/host/agent-tools.ts:834) 先按 `16000 / 模型数` 字节截断每个结果；[src/host/prompt-runtime.ts:402](/Users/synear/.codex/worktrees/gea-prompt-optimization/dsh-gea-plugin/src/host/prompt-runtime.ts:402) 随后把这层已截断文本存入新证据库。[src/host/prompt-evidence.ts:96](/Users/synear/.codex/worktrees/gea-prompt-optimization/dsh-gea-plugin/src/host/prompt-evidence.ts:96) 又统一告诉模型用 gea_evidence_read 读“完整正文”，与旧包内部的 gea_module_mcp artifact 提示不一致。嵌套 result 字符串还会在投影中被再截为800字符。

**影响**：新证据引用能完整恢复外层工具回执，却不能恢复被上一层切掉的业务正文；模型反复读相同引用，消耗额度。不是文件读取失败，也不是放宽授权就能解决。

**建议**：保留一个带授权来源的完整产物和一种主回读契约；业务记录结构化投影，不把嵌套JSON当长字符串切开。保持旧 artifact 可用，不能删除唯一完整来源。

### IQ-03 / P1：知识结果绕过结果预算，首轮短了，后续仍迅速膨胀

**事实**：基地规则追问仅问重复键和版本回退，14次调用返回工具正文151,731字符，其中5次 lightrag_query_data 合计143,893字符，单次22,985～34,296字符。

**已确认根因**：所有 gea_module_mcp 被统一标为 mcp 证据；知识查询没有 Cube query_business_data 的授权回执，[src/host/prompt-runtime.ts:382](/Users/synear/.codex/worktrees/gea-prompt-optimization/dsh-gea-plugin/src/host/prompt-runtime.ts:382) 为避免凭空创造可复用权限，直接返回原正文，绕过后续6,000字符投影。原保护方向正确，但知识类结果缺少自己的有界返回和读取方案。

**建议**：按知识与业务查询区分证据类别，在各自授权范围内提供有界片段和明确续读。不能通过取消授权检查解决体积问题。对话预算应覆盖工具历史，不只测 system+tools。

### IQ-04 / P1：最终答案否认已经获得的证据

**事实**：
- 销售先收到3次成功 aggregate，coverage=complete，且含 totals/groups；最终称“未取得任何聚合结果”。这些结果不一定完整回答省区任务，但不能说不存在。
- 全链已经读到分仓、经销商的授权目录，最终却称这两层没有可见授权通道/字段。
- 郑州大日期问答中，证据回读成功返回6,000字符；最终称“只有引用ID、未读取正文”。本轮未完成完整查询是真，完全没读过是假。
- 产销上一轮已加载含95%阈值的完整 Skill，追问却称“未加载阈值”。

**根因分层**：答案与真实回执冲突已确认；末轮缺少“哪些成功、哪些失败、哪些仅部分完成”的结构化核对是实现缺口。模型在长工具历史中偏向最后片段、已加载短回执缺少相关规则提示，是合理解释，但未证明为唯一内部原因。

**排除项**：另做最小模型请求捕获，跨轮去重时原 Skill 正文仍在实际发送的 messages 中，没有复现“代码误删了唯一正文”。因此不把 instructionVisible 直接判成已证实的失效实现。证据：[可见性对照](inventory-qa-2026-09-26/skill-visibility.json)、[正文存在检查](inventory-qa-2026-09-26/rule-body-checks.json)。

**建议**：最终作答前按任务项与成功回执核对；补充来源索引、有效事实和缺口，区分“未查/已查部分/成功/后续失败”。先验证对真实模型的改善，不只加一句“不得忘记”。

### IQ-05 / P2：元数据探索循环，20次额度耗在目录上

**事实**：经销商首问21次工具尝试、0次 Cube；全链首问20次、0次 Cube。郑州大日期前期反复读取相同目录和 Skill，最后只完成识别仓库和查快照，没执行完整大日期 Top10 查询。第21次是被额度守卫拒绝的尝试，不代表执行突破20次限制。

**已确认实现因素**：旧 `replayOf`（[src/host/agent-tools.ts:254](/Users/synear/.codex/worktrees/gea-prompt-optimization/dsh-gea-plugin/src/host/agent-tools.ts:254)起）仍重放全文/前缀和告诫，新调用预算继续计次；既有重复治理与新额度没有基于业务进展衔接。能力目录、consumer编码、Skill名称三套标识也出现混用。单纯把20改40不能解决无进展探索。

**建议**：目录变化感知与参数规范化去重、给出下一步可执行查询模板；为同任务的实际取数与最终交付保留额度。复杂额度按可观察任务进展决定，不靠模型自行记得申请。

### IQ-06 / P2：工具 Schema 没讲清边界，真实模型频繁撞参数墙

**事实**：证据回读出现 limit=18000、8000、7000，均超过6000；基地、产销、经销商反复给 gea_skill 传 offset=0；基地 Cube order 曾传数组对，真实 Schema 要对象；全链/分仓把 consumer 名称当 Skill 名称。

**已确认根因**：gea_evidence_read 的 offset/limit 仅暴露 integer；gea_skill 也未在参数处写明起点1和上限200，运行时才拒绝。两个工具共用 offset 这个名字却分别从0和1开始。严格拒绝非法参数本身正确，前置调用契约不够清楚。Cube order已有完整Schema，其错误属于模型没有按Schema调用，不能归咎于字段缺失。

**建议**：在参数描述与错误回执中给完整合法边界、默认值和可复制修正值；统一或显式区分行号/字符偏移；能力目录明确 preset、consumer、Skill 的映射。保留严格校验。

### IQ-07 / P1：基地“缺货”被替换成“库存为零的记录行”

**事实**：基地查询按 current_inventory≤0 + row_count 排名，答案将零库存行称为缺货行、比率称为缺货率，再评价哪个基地最严重。它披露了行数口径，但没有证明这等价于业务缺货；本地规则明确提示缺货可与正常/偏高库存状态重叠。

**已确认根因**：实际 safety_stock 目录只有 row_count 度量，数量字段是维度；缺少可直接调用的受管缺货聚合，模型转而回答容易计数的替代指标。现有提示有禁止错误口径的原则，缺少可执行的缺货口径与查询契约。

**建议**：没有正式缺货数量/满足口径时，只能明确交付“零库存记录分布”，不能升级为业务缺货结论；补齐受管数量聚合和业务阈值。不能让模型拉200行心算充当全量。

### IQ-08 / P2：后端能力缺口与跨 Agent 试探混在一起

**事实**：当前账号下 aps 和 full-chain-inventory 返回 no-authorized-resources；产销正确停下，全链却继续尝试 branch/dealer/aps/base 等多个 consumer，且重复查自己的空授权4次。工具明确告知“不轮换身份试探”，但实现只校验注册consumer和该consumer实际授权，未对这种后续行为收口。

**已确认实现因素**：应用对 no-authorized-resources 只返回文字提示，没有形成任务范围内的后续探索限制；当前可用资源由服务端授权快照决定。为何这两个 consumer 的资源为空，需要平台核对配置或映射，不能由本次输出断言具体漏配项。

销售对照另外发现：部分 M/Z 聚合筛选返回 GEA_AGGREGATE_FILTER_UNSUPPORTED，宿主检测到上游返回的 orderType 不符合请求。保护没有放过不可信汇总，这是接口/筛选契约缺口；不能把这类错误当所有先前成功结果作废的理由。

**建议**：区分账号未配置、工具不支持和真实空数据；独立的合法跨业务查询要有明确依据，授权为空后的无目标轮换要停止。本次只证明行为违反已声明策略，没有证明绕过后端授权读取了未授权行。上游配置/筛选问题需平台核查，不在本轮擅自补权限。

### IQ-09 / P2：超时被改写为普通取消，诊断信息丢失

**事实**：长会话分仓规则题120.0秒后以 Request aborted / UNKNOWN 结束，未触发测试的240秒取消阈值；新会话相同题44.4秒完成且主要规则正确。

**已确认代码根因**：`src/shared/transport-signal.ts` 把所有 signal.reason 转成 AbortError("Request aborted")，包括TimeoutError；[src/shared/net-error.ts:82](/Users/synear/.codex/worktrees/gea-prompt-optimization/dsh-gea-plugin/src/shared/net-error.ts:82) 随后按普通取消返回，无法走超时分支。确定性最小测试已复现。

**仍待确认**：这一次为何需要超过120秒——长历史、推理耗时或上游/网络慢，缺少服务端trace，不能仅凭新会话变快就断言。超时原因被抹掉是确认问题，原始慢因尚未确认。建议保留安全的超时分类、阶段、请求耗时，继续剔除可能含会话事件/凭据的原始 reason。

## 正向结果与测量边界

- 六个Agent首轮 system+tools 日志均低于12,000字符：分仓6,769，基地6,743，全链6,743，经销商6,748，产销6,744，销售8,502。**不含后续工具历史，不是token数**；不能从这些数得出整个会话占用一直很低。
- 受管授权仍参与查询；没有把无授权说成库存为零。产销实际问题正确停下。
- 经销商追问正确区分授权客户与库存客户，也没有仅凭高库存判滞销。
- 新会话分仓示例正确保持缺计划为未知、在途只扣一次。
- 最小 Skill 可见性对照通过；模型归属和超时分类两个最小复现按预期红灯。没有靠修改业务源码或放宽测试让它们变绿。
- GEA_CATALOG_NOT_JSON 在首条分仓问题出现一次，随后相同查询恢复；未拿到可审计的原始上游失败包，不单独给它编造根因。

## 推荐处理顺序

1. 先处理 IQ-01 / IQ-02 / IQ-03：统一模型与工具身份、打通唯一完整产物回读、控制知识正文体积。
2. 然后处理 IQ-04 / IQ-05 / IQ-06：用真实回执约束最终交付、停止无进展探索、补全参数契约及别名映射。
3. IQ-07 / IQ-08 需要业务与平台一起确认缺货指标、Cube授权和筛选契约；不以扩大权限或模型心算代替。
4. IQ-09 修复分类后再测长会话耗时，记录服务端trace。用同一14题集做前后对照，并追加页面绑定场景；不只运行脚本固定好的工具序列。

本轮没有修复这些新问题，也未推送、发布或切换客户端。候选源码仍为原提交，新增内容仅为测试脚本与问题报告。
