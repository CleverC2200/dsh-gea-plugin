本轮直接读取3441预览环境的三份会话日志、工具证据和Host日志，做只读回放及真实预检函数探针。没有修改运行代码、重启服务、替用户重新发问或调整权限。

结论：三轮都取得过有效数据，不能归为整体无权限。货龄题取得了可核对的数量，但丢了已确认单位；目标库存题错误否认已返回的SKU字段和数量目标规则；缺货题在错误查询、反复探索之后耗尽额度，最终输出协议文本，被系统误记为完成。

## 2. 高于目标：规则和字段已经返回，随后被忽略

关键证据：

1. 事件seq22的目录明确列出`agents_scm_branch_plan.material_code`、`material_name`，描述也是计划快照×目标月×版本×来源×分仓×SKU。并非无SKU维度。
2. 后续加载的`inventory-fc`正文明确给出`order-net-gap-v3`：计划日均=`ceil(本月出货计划/月天数)`；目标库存=`(周期天数+3)×计划日均`。数量目标不是必须有一个名叫“target_stock”的源字段才存在。
3. 实际查询主要抓取`bi_target_amount`等金额预算与状态，没有沿数量目标公式取得完整的SKU出货计划、补货周期、有效版本和比较库存。
4. seq98自行查询`sku_code`，该名不存在而被本地拒绝。错误仅证明`sku_code`不是合法成员，不证明`material_code`不存在。
5. 最终答复仍声称“没有SKU维度”“只有分仓/提货点级金额目标”，把一次错误拼写扩大成模型能力缺失。

补充问题：`gea_capabilities(skill="branch-inventory")`把consumer名当技能名，返回`GEA_SKILL_UNAVAILABLE`；后续真正的`gea_skill(name="inventory-fc")`已经成功，最终仍以技能未加载来解释缺口，混淆前后状态。

根因确认到：**业务词到技术成员的映射失败，且成功返回的字段与规则没有被最终结论正确采用。** 不能仅通过再加一句“不要编造”解决。

正确后续路径：锁定长沙分仓实体A020及提货点映射→明确目标月、有效版本与来源→使用`material_code`读取目标公式所需输入→通过已有可信计算或受管派生指标比较。若缺计算能力、字段值或比较口径，应准确报告该缺口。本轮没有重新查询全部输入，不能宣称这条计算链已完成业务验收。

## 3. 货龄：数据已取得，单位和读取效率仍有问题

`ev-de84569f2accadd1c1326ef8`中15行SKU汇总可用量加总为199，另一个合计查询也是199；最终表格的总体计数与合计有依据。其中一个SKU可用量为0，应表述为“有超90天记录”，不能直接推断现存量为0或已被占用/锁定。

seq25与seq62的目录两次返回：`available_qty_sum`是`qtylive`源列合计，**单位件（业务2026-09-27确认）**。最终仍称“字段未标注单位”，是忽略已得事实。最后的本地上下文投影仍保留这两条目录事件，因此不能解释为从未返回或已在本地投影中消失；网关是否另做消息改写尚无出站正文证据。

效率问题：

- 前期把所有快照的明细和日期探索一起查询，之后才限定2026-09-27；过程中还出现过`>=90`与`>90`两种查询。最后使用的是`>90`汇总，但前序扩大了读取量。
- 先取得物料编码和库存，后补名称及合计，增加往返。经确认同一模型粒度后，编码、名称与受管数量通常可在同一条分组查询中取得。
- 已用过dataset行读取，后面又回到原文字符读取；同一仓库候选证据两次从offset0开始读，未沿nextRead续读。
- 一条仓库候选的原始行JSON约262字符，带多层产物包装后5,736字符；15条编码/数量约1,581字符，包装后11,196字符。原始证据应保存，但让模型不断读取转义包装增加了成本。

改进重点是稳定的结构化结果与明确单位字段，默认按dataset行读取；仅需查产物元信息时才读取原文。不要把“完整产物可恢复”误做成“每题必须读完整个包装”。

### 下游错误：已知输入错误，尚缺内部错误日志

报错调用是seq41，`zero_avail_batch_by_date`使用`operator: "="`。当前Schema仅把operator定义为string，预检只检查非空，不验证允许的操作符；本轮用真实`preflightCubeArguments`回放，确实放行了该操作符。

下游只返回`MCP_UPSTREAM_TOOL_ERROR`，没有内部异常。排查定位：

- requestId：`f280ee91-75d8-4db9-9e69-7da91eda873e`
- traceId：`12d32d25-fba3-40a0-8816-17d24e671a33`
- auditId：`11507432-54b3-4de3-a106-91fefacf6b7a`

因此可以确认“非法/非约定操作符未在客户端拦截”，但不能仅凭统一错误宣称下游唯一根因已查明，更不能定为权限不足。需要用上述ID定位服务端原始异常；本轮没有登录下游服务器查该内部日志。

后续联合实施阶段补查：Cube服务端03:02:13.635Z的`32ebccd4-0f48-4218-b723-cd3bdd0932dc-span-1`事件包含相同A020查询及`available_qty operator="="`，原始错误是`Invalid query format: "filters[1]" does not match any of the allowed types`。详见[联合交付](aps-fc-joint-delivery-2026-09-27.md)；这是补充的服务端证据，原GEA requestId与Cube事件ID未在日志中直接串联。

### 缺货语义与查询范围

这一轮未取得订单需求、备单剩余或正式缺货字段，主要沿零可用库存探索。零可用库存不等于当前履约缺货。seq55的SKU汇总还没有单一快照过滤，存在跨日累计风险；返回200行恰好触及limit，来源已提醒全量性不足。这些结果即使最终显示，也不能直接命名为“当前缺货SKU清单”。

### 可确定复现的协议检测漏洞

当前`src/host.ts`和已构建Host的检测规则只匹配紧接DSML标记的`tool_calls`或`invoke`。实际返回为`<｜｜DSML｜｜ calls>`，有空格且入口名是`calls`，不匹配。

本轮直接用源码中的正则测试捕获文本，结果为false。日志seq111保存了协议文本，seq113仍标`completed`。这是明确的客户端漏洞：**协议内容未执行，却被当成普通最终答案结束。**

额度耗尽后的`tools=[]`也已确认：最后请求的toolSchemaChars=2。隐藏所有工具后模型继续输出协议文本，是本次故障链的观察结果；是否一定由清空工具导致，需要改变单一变量做后续模型对照，不能由一条日志断言。

## 5. 为什么反复出现系统提示词，以及上下文为什么变大

三轮轨迹分别记录11、11、9条`system/message`快照，随技能加载、读取状态和额度变化更新。最后的本地contextBreakdown每轮只有**1个system节点**。所以截图中的多张“系统提示词”不能直接理解为一次请求同时塞了十份相同系统提示。

但上下文增长是真实的：

| 会话 | 首次messages字符数 | 最后messages字符数 | 最后本地上下文估算 |
|---|---:|---:|---:|
| 高于目标 | 1,932 | 73,782 | 15,899 heuristic tokens |
| 货龄 | 1,928 | 80,407 | 17,198 heuristic tokens |
| 缺货 | 1,924 | 76,962 | 16,559 heuristic tokens |

messages字符数不含另列的工具Schema，后者多数请求为6,423字符。以上均不是provider真实token计量。增长主要伴随工具结果、重复目录、技能重读和证据包装进入历史；公共提示词预算只统计当前组装的system/tools等，不能代表完整历史请求大小。

在本次预览中，“一轮后上下文接近半窗”的观感有日志依据，但不能据此说初始全局提示词就已占一半。若要精确归因，后续应记录脱敏后的每类消息条数、字符数及provider usage，并核对实际送入网关的system条数。
