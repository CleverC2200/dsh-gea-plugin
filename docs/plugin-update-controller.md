# 公司插件更新与启动恢复

公司更新把依赖安装与用户资料分开：官方 `runProfilePnpm` 在候选目录安装，现有 `PluginStore` 管理准备、选择、试启动与上一可用版本。实际公司桌面入口为 `official-main.cjs` → `company-desktop.mjs` → `prepareCompanyBoot`，完成选择后加载原官方桌面主程序。Core、身份和凭据 owner 不变。

受管发行使用 `managed-suite` 发行策略。旧读取器拒绝该策略，不能继续原位安装；双端桌面打包也拒绝旧 `suite` Host。新入口在既有更新配置中写入 `installationProtocol: 1`，旧 Host 因不支持新合同而阻断更新；业务与原来源仍保留，新 Host 接收此合同。

## 安装与确认

`check` 校验签名频道、Core 支持范围和整组兼容；`submit` 与 `submitBatch` 持官方 profile 锁重核计划、活动 Host、来源与 writer。安装沿用官方 pnpm、既有 store 和现有进程监督，禁用生命周期脚本、pnpmfile、自动 peer 安装和新 bundle 激活。候选图通过版本及非安装字段检查后排队，当前进程继续使用原图。

桌面下一次启动才挂载候选图。安装目录位于原 profile 的 `gea/installations/<Core SHA>/`，`node_modules` 使用受管链接；只切换依赖声明、锁和模块，保留同一个用户 profile。Host/client 的实际版本与模块目录一致后才确认可用。旧进程、磁盘版本和旧浏览器模块不能完成在线操作的重启确认；观察仍受认证、nonce、页面、进程及模块来源校验。

普通 Core 的手动插件安装仍由官方 PluginManager 管理。GEA 在线整组更新需要公司桌面的受管安装入口；未迁移的客户端不能继续原位写依赖。发行接收需同时包含桌面入口与对应 GEA Host，不能只分发 Host 单点补丁。

## 中断与回退

| 中断位置                                     | 下一次启动                           |
| -------------------------------------------- | ------------------------------------ |
| 下载或候选准备                               | 启动原可用图，保留失败候选与日志     |
| 候选已排队、尚未启动                         | 完整性与来源仍一致时试启动           |
| 试启动未确认即退出                           | 选择上一可用图                       |
| 主程序、页面或 renderer 启动失败，或确认超时 | 记录失败并经正常退出、重启回退       |
| bootstrap 失败                               | 恢复入口跳过安装，启动已保存的可用图 |

准备锁与选择锁分开。候选写者仍存活时不能继续准备同一份候选，但不阻止独立可用图启动。POSIX 沿用受控进程组，Windows 沿用原生 Job。日志损坏阻断新的更新，受管候选失败不再使可用版本永久停在“状态未知”。原位旧操作只有在确认 writer 已停止后才迁移；未知写者仍需保留现场。

在线、统一客户端更新的回执在启动回退时同步失败，原回执另存。schema 1 的首次读取保留 `receipt.legacy.json`；个人 Agent、Skill、Session、草稿、凭据和非安装配置不随依赖图恢复。失败材料及旧目录不在启动恢复中清理。

## 验证边界

公开 Host 路由测试使用真实 pnpm、新进程 Loader/client 与可读的 Core 持久会话。`scripts/desktop-gea-upgrade.test.mjs` 汇总安装图、实际启动协调器及迁移检查；`company-update.yml` 另验 Windows 当前发行运行时与候选公司入口，保留来源绑定、窗口、进程中断和资料读回证据。此候选运行时验收不代表签名安装器发行、员工原故障资料或正式频道已生效。
