# 插件构建被桌面安全余量误拦截

销售计划客户端更新时，已有依赖的 GEA host/client 编译因可用空间约 18.5 GiB 被拒绝。统一容量策略为所有操作保留 20 GiB，再加操作预算，导致纯插件编译也要求 21 GiB。

用户明确指出插件构建不应受此门槛限制，并要求提交 PR 合并。修复按插件与桌面两类操作选择安全余量，具体预算由 [buildPolicy](../../../../../scripts/build-admission.mjs) 维护。原有在途预留、输出目录互斥、重型写入串行和过期 owner 检查保留。

容量边界反例在旧实现失败；修复后构建准入、开发任务、构建入口与三包交付共 39 项回归通过。新增测试分别核插件编译、打包、watch、依赖准备与桌面、SDK 的精确边界。该变更只影响开发构建工具，不修改客户端业务、用户数据、服务端或 DMS。

首次 CI 的单分片并发执行暴露打包与编译测试共享卷锁的问题。本地组合执行复现 `BUILD_VOLUME_BUSY`，单独运行相关测试通过。构建、交付和版本戳测试现在将锁文件限定在各自临时目录，保留全部原断言和生产卷锁逻辑；加入版本戳测试后的 41 项并发回归通过。首次远端失败记录保留，修正版仍须通过完整必需 CI 才能合并。

第二次远端测试为 228/229 通过，仅剩 Workbench 独立包检查失败。原结构化结果只记录文件计数，未保留具体断言。测试 reporter 现将失败名称与经遮蔽、限长的错误文本写入同一执行回执，原退出码、计数和失败判定不变；reporter 与执行回执的 37 项回归通过。

第三次远端为 265/266 通过，回执定位到独立包检查读取未设置的 `GEA_TEST_SOURCE_INPUTS`。该检查原本直接引用底层源码解析器，未经过已有 profile 测试入口，因而没有声明冻结资产准备需求。它现在从现有 profile 入口复用同一个解析器，CI 依赖图能准备所需源码资产和浏览器。新增定向回归核实际计划包含该检查，并声明 runtime 与 browser；实际独立安装和浏览器断言保持。
