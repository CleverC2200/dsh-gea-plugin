# 历史插件占用：诊断与清理范围

状态：2026-09-27 用户随后授权“按照推荐的方案全量执行”。自动版本回收、下载缓存保留、核心分层已经实现并完成隔离验证，见 [实施记录](desktop-install-storage-implementation-20260927.md)。未对本机或同事的真实用户目录手工执行清理；实际释放量仍需目标机器的目录证据。

## 修改前诊断证据

- 正式 0.0.22 安装包中 `plugin-store.mjs`、`updates.mjs`、`client-installer.mjs` 与当前工作树对应源码逐一摘要相同。
- `PluginStore.prepare()` 每次复制 node_modules、package.json、packages、pnpm-lock.yaml、pnpm-workspace.yaml，保存独立版本目录。版本激活及启动确认不会淘汰旧版本。
- 隔离复现使用实际 PluginStore，完成 6 次 prepare → activate → beginBoot → confirmBoot。目录仍包含 test-1 至 test-6；active/verified=test-6，previous=test-5，test-1 至 test-4 已不被这些状态引用，仍未删除。
- 正式包的上述更新图共 21,824 个文件，逻辑大小 369,100,221 bytes，约 352 MiB。实际更新图会变化；逻辑大小不等于文件系统分配量，不能据此声明任何同事机器已测得的占用。
- 常规准备失败会清理本次 staging；进程崩溃后的遗留 staging 为避免误删仍运行的安装子进程而被保留。
- desktop-downloads 按摘要/文件名保留下载完成的安装包，只自动移除本次下载的 part 文件。
- 安装提速诊断包复用原应用内容，未改变以上策略，因此不会自动释放历史插件占用。

## 本轮实施的保留边界

| 对象 | 建议 |
| --- | --- |
| 正在运行、当前选择、已验证回退、正在启动、待重启更新 | 必须保留，异常状态宁可不清 |
| 正常状态下更早、已不被引用的自动更新版本 | 新版本启动成功且更新器空闲后后台清理；通常保留当前与上一套可用版本 |
| 用户手动准备的本地版本 | 不按自动更新版本规则直接删除，保留明确选择/固定版本的能力 |
| staging/prepare.lock | 先确认所有者和安装子进程已结束，不能仅按目录年龄删除 |
| 已下载旧安装包 | 与插件版本分开统计；清理时保护正在下载/准备打开的文件，采用明确保留策略 |
| pnpm 或其他共享缓存 | 先确认归属和实际占用，不顺带执行全局清理 |
| 登录、会话、工作区、个人配置、安装包内 baseline | 不属于历史插件清理对象 |

清理放在确认正常启动后的空闲阶段，避免重新拖慢 EXE 安装或首次打开。状态引用、并发准备、手动切换和失败回退都需要回归验证；不能只按“最新两个目录”或修改时间做删除。

Windows 默认用户数据位置通常为 `%APPDATA%\dsh-gea-desktop`，但自定义数据目录仍需按实际配置识别。需要确认同事的主要占用属于 `plugins\versions`、`plugins\staging-*`、`desktop-downloads` 或其他目录，才可给出可删除清单和预计释放量。
