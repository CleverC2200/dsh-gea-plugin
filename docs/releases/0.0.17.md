# GEA 0.0.17：角色审批与流程通知分离

## 本次插件改动

- 保留 0.0.16 的组织、有效版本和状态可见范围。多角色取可见范围并集，用户明确选择本次审批角色。
- 取消通知任务授予审批权限；可见且拥有审批角色的未完成单可以进入审批操作，包括原先只读跟踪的推进单和本人发起的退回单。
- M/Z 的请求携带操作角色；默认值、保存结果和纠偏回读按该角色取字段，不从当前通知状态推断操作角色。
- 状态 0、5、10 均禁止写入；移除状态 10 的独立 SAVE 特例。纠偏审批不再受 approvalOpen 日期开关限制，保留月初终审、版本、数量与快照校验。
- 新角色契约允许非当前角色审批后通知位置保持不变。退回核对操作角色的上一个配置节点；终审回执必须包含所有必需角色的有效通过结果。
- 同一角色操作重试绑定原始请求和幂等键；改变角色不能复用旧请求。

## GEA 服务端兼容边界

本次发布的是插件，未修改或部署 GEA 后端。登记的后端现有接口仍按当前流程节点写确认字段，因此不能直接把“区域在省区阶段确认”发给旧接口，否则存在写错层级的风险。

明细新增显式契约（仅由服务端返回，客户端不能自行宣告支持）：

```json
{
  "actionContext": {
    "versionId": "version-id",
    "status": 2,
    "snapshotHash": "64位小写十六进制快照摘要",
    "policy": "role-visible-v1",
    "allowedActions": [],
    "roleActions": [
      {"role": "region", "allowedActions": ["SAVE", "APPROVE", "REJECT"]}
    ]
  }
}
```

新请求携带 `approvalRole` 和 `approvalPolicy=role-visible-v1`。回执携带相同 `approvalRole`；若进入 5，还须返回对当前结果有效的 `approvedRoles`。通知字段 `workflowApproval` 只作提醒，不能替代角色授权。

服务端宣告该契约前必须实现：组织与角色授权、角色对应字段写入、审批依据变更后的结果失效、逐级退回、有效审批结果持久化、全部必需节点通过后的回写触发以及事务和幂等校验。完整业务规则见 `specs/sales-plan-role-approval-v1.3.md`。

旧服务：保留有可信角色证据的当前节点操作；跨节点角色可查看操作入口，但显示升级服务端提示并禁止发送。不会把跨节点请求降级成旧接口的当前节点操作。仅靠通知取得权限的用户不再能审批。此限制意味着插件更新本身不能让真实 GEA 完成全部 V1.3 后端行为。
