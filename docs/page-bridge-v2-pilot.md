# 页面自述 v2 试点（快照 / 改单）结论

本文记录"宿主扫页面" 与 "页面自己报" 两种元素来源的试点结论：各自代价、当前选择、
以及什么时候该换。随实现一起维护。

## 1. 两种来源

| 来源 | 谁生成元素目录 | 用在谁身上 | 实现 |
| --- | --- | --- | --- |
| `self-report`（v2 自述） | 页面自己上报"这一屏有什么"，并自己收改单 | 原生工作台页面 | `src/workbench/page.tsx` 上报 → `src/host.ts` 路由 `agui/workbench` |
| `dom-scan`（宿主扫，回退） | 宿主把适配器注入同源页面，扫真实渲染结果 | 从 web 迁过来的业务页面 | `src/html-page-scan.ts` 注入脚本 + `src/html-plugins.ts` 的 `page-bridge` 方法 |

两种来源产出的都是同一份"页面目录"：宿主拿到的字段、执行的通用动词、以及落地时的
硬校验完全一致，模型侧看不到差别（除了结果里的 `pageSource`）。

## 2. 回退规则

- 页面自己报了元素 → 用自述的（`source: "page"`），`pageSource=self-report`。
- 页面没实现自述 → 用注入脚本扫出来的，`pageSource=dom-scan`。
- 两者都没有（页面还没渲染、被清空、切走）→ 报 `null`，宿主**立刻注销**该会话的页面工具。

切页、切会话、关闭页面都会走最后一条：不留上一屏的元素目录（这也是"点了没反应/超时"的根因）。

## 3. 试点结论（原生工作台 = 自述；迁移页面 = 宿主扫）

**收益**

- 迁移过来的 6 个业务页面**不用改一行页面代码**就能被对话读、改草稿：宿主在服务端把
  适配器注入页面 HTML，扫描与执行都在页面自己上下文里做，框架 sandbox 与页面 CSP 都不用放宽。
- 自述页面（工作台）不需要扫描：元素本来就由页面按状态生成，比扫 DOM 准。
- 两条路都落在同一套宿主硬校验上：只读元素改不动、提交/审批类要 `confirm`、超出上限的目录
  在页面侧收口而不是放宽宿主规则。

**代价**

- 扫描是"按当前 DOM 推断"，页面结构大改（表格换成卡片、控件换成自定义组件）时元素会少认，
  需要按优先级挑（先保控件与行，再保只读文本）。
- 自述要求页面显式上报，迁移页面要升级到 v2 才能享受"更准"，属于页面侧工作量。

**是否推广**：是，但分两步走。
1. 现在：迁移页面用宿主扫（零改页面），自述页面保持自述。
2. 以后：哪个迁移页面开始频繁改结构、或者扫描认不准，就把那个页面升级成 v2 自述
   （`protocol: self-report`），宿主消费方式不变——这正是"垂直声明 + 水平实现"的第一步。

## 4. 同一用例怎么双跑对比

对同一个会话，分别在自述与扫描两种模式下跑同一组用例（读一屏 / 改可编辑项 / 改只读项被拒 /
提交类先要确认 / 切页不残留），比较：

- 元素数量与 id 是否稳定（同一屏重复扫描应得到同一批 id）；
- 改草稿后页面上的值是否真的变了（回执 `applied:true` + 页面上可见）；
- 只读项是否**没有**产生任何写请求；
- 结果里的 `pageSource` 与 `draft.outcome`（`applied` / `failed` / `timeout` / `rejected`）。
