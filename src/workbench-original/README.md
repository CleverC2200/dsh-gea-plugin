# Original GEA sales-plan workbench

Copied from AionUi `packages/desktop/src/renderer/pages/assistantSurface/workbenches/regionalApproval` at commit `55d12cd60248c6084afd76bba816638a79af36de` (Apache-2.0; retained in `LICENSE`). The source workbench is React and CSS Modules rendered inside `BusinessSurfaceShell`; there is no independent sales-plan HTML file in that checkout. This copy is intended to be compiled into the plugin's separate center HTML document.

The original JSX, styles, query generation, exact-decimal projection, version comparison, dialogs and workflow models are retained. Changes redirect source imports to local files, make NodeNext file extensions and a numeric reducer type explicit, and replace the AionUi IPC and chat imports with `bridge.ts` and `session-context.tsx`. No AionUi process or conversation implementation is imported. `contracts.ts`, `salesPlanWorkflow.ts`, `http-error.ts`, `storage.ts`, and the surface translations are copied or extracted from their source owners. Storage prefixes are isolated to `gea-dsh`, so old AionUi browser state is not adopted.

Before mounting, call `bindWorkbenchHost(host)`. Supply all methods declared by `WorkbenchHost`; absence of a binding throws instead of rendering fabricated records. Pass `stateScope`, `t`, `onContextChange`, the authenticated `permissionCodes`, and `liveActionsEnabled` to `RegionalApprovalWorkbench`. Wrap the component with `WorkbenchSessionProvider` using the actual DSH session ID. Publish the complete `onContextChange` value to the parent host; it includes selected rows, visible rows, scope, revision input, authority and evidence status.

Bundle this document with React, ReactDOM, `@arco-design/web-react`, `@icon-park/react`, i18next, and `xlsx-republish`. Load Arco CSS, then `theme.css`, and compile `.module.css` with CSS Modules (`local-css` in esbuild). The two locale JSON files use an i18next `common` namespace. The copied workbench renders some legacy fixture code only when its query client is explicitly `null`; a live plugin must supply the host adapter, never `null`.

The host maps the original API methods to GEA: `GET periods`, `GET plans`, `GET plans/:planId`, `GET plans/:planId/versions`, `GET plans/:planId/logs`, `GET plans/versions/:versionId/skus`, and `GET plans/:planId/compare`. IDs and decimals remain strings. `action` writes `POST plans/versions/:versionId/actions`; `submit` writes `POST submissions` and has a separate server capability requirement. The adapter enables approval from a real `actionContext`, legacy authenticated node permissions, or a freshly read server-assigned notification matching `sales-plan:version:<versionId>`. The notification grant enables only APPROVE/REJECT through the sales-plan action endpoint; generic notification actions are not used for sales plans. Stage filters browse server-visible data independently of action permissions. Missing or failed task discovery leaves approval disabled. Stateless SKU advice uses `modelInference.invoke`; it is independent of the right-side DSH conversation.

Returned rows expose a resubmission dialog that reads the current version and SKU data, edits quantities, and validates the configured next status and original `orderType`. Customer returns require an OPEN period; approval-role returns do not inherit that client-side window restriction. The Host retains the authenticated user ID for attribution. The standalone adapter currently leaves submission disconnected: the dialog explicitly disables confirmation until the service-identity transport and caller authorization are connected. Local editing does not write business data. This is not a separate first-submission page.

The submission endpoint is `POST /api/v1/internal/sales-plans` for both first submission and resubmission. It requires service-identity Authorization, Idempotency-Key and X-Request-Id. A connected adapter must validate the caller, tenant and source version before invoking the service. The form retains one immutable attempt after dispatch and only retries an uncertain outcome with the same key. A receipt must identify the expected successor; readback must show that successor effective, its predecessor retired, and a matching RESUBMIT log before the queue is refreshed. Confirmation-field inheritance and live service authorization still require acceptance.

The standalone document loads workflow rows through `/api/gea-proof/workflow/config` before loading periods. The Host requires its current GEA login, keeps delegation tokens server-side, validates complete SQL paging and configured chains, and cancels reads on identity changes. Document loads reject aborted or superseded results; queue, progress and analysis queries require successful period loading. Configuration failure clears the workflow projection. Local workflow rows serve fixtures only in this document. XN and other shortened chains resume through their next configured node, including non-contiguous configuration levels; approval is independent of the submission window. These projections do not grant write authority.

Sales-plan action errors preserve the upstream HTTP status and sanitized diagnostic fields. A 409 response is a confirmed conflict, not an unknown transport outcome; the dialog shows the backend explanation, including unresolved workflow assignees. Transport uncertainty retains same-intent retry behavior.

SAVE requests carry a plan ID for Host-side preflight. The Host re-reads that plan under the current login, requires an explicit server SAVE capability, and checks the effective version, status and snapshot hash before writing. Status 5 is rejected before any save request. A changed snapshot after an unknown result prevents another write and requires reconciliation. The UI uses object capabilities independently of legacy menu roles; save readback also rejects changed sequences or plan types and unknown or duplicate adjustment codes.

The backend `pro` source at `cf388b27` still exposes only APPROVE/REJECT with expectedStatus 1–9 and accepts active approval states 1–4 in the action service. It does not expose SAVE or an action snapshot field. Therefore the current real service cannot complete status-10 same-version saves. Isolated Host and Chrome SAVE fixtures verify the adapter and readback behavior only; they do not demonstrate a deployed SAVE contract or real persistence. DMS remains mock-only.
