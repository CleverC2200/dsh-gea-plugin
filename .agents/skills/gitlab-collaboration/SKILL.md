# GitLab 协作与错题本

以项目 `.team-skills.json` 声明的远端主线为团队来源；本机安装副本、旧工作树和版本号都不能单独证明最新。团队源文件位于 GEA 仓库 `.agents/skills/gitlab-collaboration/`。命令在业务仓库根目录运行。

## 拉取与技能检查

- 优先用 `python3 scripts/team-workflow.py sync`：刷新已核对 URL 的远端，只对主分支做干净、无分叉的快进；即使源码没有新提交，也检查两项技能。
- 每次开始协作、合入前及发布前运行 `python3 scripts/team-workflow.py check`。读取退出状态及每项技能的来源 SHA、缺失/差异文件；联网失败是“未核验”，不是最新。同版本不同内容也是差异。
- 缺失或落后的受管理安装副本用 `python3 scripts/team-workflow.py install-skills --apply` 更新，先备份再安装。已存在但没有安装凭据的差异、受管理文件的本地改动须人工比较，不能强制覆盖。本机专用说明可放 `references/local-*.md`，不提交团队仓库；安装器保留这些附加文件，使用相应技能时按需读取。
- `python3 scripts/team-workflow.py install-hooks` 给本仓库安装拉取后检查。已有其他 hook/core.hooksPath 时停止安装并报告，不覆盖它们。Git 不会分发本机 hook 配置；每位成员克隆后都要安装。普通 `git pull` 没有新提交时不会触发 post-merge，仍须用上述 sync/check；hook 的警告不能撤销已完成的 Git 合并。
- 两项技能都核验成功才称“规则已同步”。源码更新、技能更新、已启动会话读取新技能是三个步骤；内容更新后重新读取 SKILL.md，不把文件更新说成会话已自动加载。

## 开发、提交与合入

- 开始时记录仓库、任务分支/工作树、远端 URL 和刚刷新主线的 base SHA。多人/多任务写代码用各自工作树；已有归属工作树就复用。主线落后、未提交和分叉分别报告。
- 脏工作区先保存完整差异和未跟踪文件，逐项确认归属。普通 sync 不自动 stash/reset。确需恢复时三方比较 base、本地、最新主线，先判断旧改动是否已经合入；恢复备份不等于整文件覆盖。
- 合入前再 fetch，保留最新主线及双方意图；冲突逐块处理。检查相对最新主线的最终 diff，尤其是意外删除、版本回退和既有修复消失。禁止用强推、整文件 ours/theirs 或旧产物覆盖来省掉核对。
- 提交前为本次任务写 `docs/team/changes/<日期>-<主题>.md`，使用项目的提交记录模板。用 Git 历史作为提交事实来源，记录基线、改动目的、验证和关联错题，不能杜撰 SHA/作者/MR。提交里的记录不用填写它自己的 SHA；候选/合并 SHA 写入 MR 或后续记录。
- 通过 GitLab MR 交付，推送分支不等于合并。合入后读回 MR 和目标分支，记录最终 SHA。Git 作者只代表配置身份，不足以判定由哪个人或 Agent 操作。插件发布另用 dsh-plugin-release；协作记录不授予发布权限。

## 错题本

排查前按模块/症状搜索 `docs/team/lessons/`。发现有复用价值的问题时新建独立文件，减少多人编辑同一大文档的冲突；同一根因更新原条目，引用本次提交/MR，别重复建条目。

按 `docs/team/lesson-template.md` 记录：现象、最小复现、已证实根因、引入/修复提交、证据边界、遗漏的检查、今后检查位置、当前状态。区分原始遗漏、合并覆盖、构建/客户端陈旧；没有证据就写未知。记录不含凭据或真实客户数据。

修复后应把错题变成能失败的业务回归检查。例如数量变更后，检查同一 SKU 的金额、汇总与重新打开的草稿，不能只测汇总或源码字符串。没有修复/回归/发布证据时保留“待修复/待验证”，不能靠写文档关闭问题。

完成时报告源码同步、技能核验、提交/MR、错题状态以及备份位置；未覆盖或未验证的层级明确列出。
