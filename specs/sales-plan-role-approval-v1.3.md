## 一、四条核心规则

1. **可见性决定能否查看**：按授权组织、有效版本和角色可见状态筛选。
2. **角色决定能否审批**：用户看得到单据、拥有对应审批角色，且单据已提交未完成，即可按该角色审批。
3. **流程决定通知谁**：是否轮到自己、是否收到通知，不作为审批权限条件。
4. **有效审批结果决定是否完成**：配置链全部必需审批节点有效通过，才能进入待回写状态。

```text
授权组织 + 版本 + 可见状态 → 能否查看
能查看 + 对应审批角色 + 已提交未完成 → 能否审批
流程配置 + 当前通知位置 + 有效审批结果 → 通知谁
全部必需节点有效通过 → 5 待回写 → DMS 成功 → 10 回写完成
```

## 二、可见性

### 2.1 通用边界

| 维度 | 规则 |
|---|---|
| 组织 | 只看授权组织；上级可看下级，平级互不可见；客户只看自己的单 |
| 版本 | 日常列表只查 `is_effective=1 AND is_deleted=0`；历史版本只供查看和对比 |
| 状态 | 保留 V1.2 的角色可见范围，不自动扩大为本组织所有状态可见 |
| 退回 | 退回目标和发起退回角色可见；其他角色不显示 |

“拥有角色”只授予该角色在授权组织范围内的操作能力，不能跨组织获得审批权。接口必须执行同样校验，不能只依赖按钮显示。

### 2.2 Y 链角色矩阵

以下均以处于授权组织、当前有效且未删除为前提。“可审批”包含原来只读跟踪、现在允许再次确认的单据。

| 角色 | 可处理状态 | 完成后只读 | 说明 |
|---|---|---|---|
| 客户 | 0 填写提交；6 修改重提 | 1～5、10 可查看 | 客户不执行审批角色的通过/退回动作；7、8、9 不可见 |
| 区域 | 1、2、3、4、6、7 | 5、10 | 0 只在催办清单可见，不可审批 |
| 省区 | 2、3、4、7、8 | 5、10 | 1 尚未进入原可见范围 |
| 大区 | 3、4、8、9 | 5、10 | 1、2 尚未进入原可见范围 |
| 品类计划审批 | 4、9 | 5、10 | 1、2、3 尚未进入原可见范围 |

不在表内的状态，不进入该角色的普通审批列表。多角色用户可见范围取其授权角色范围的并集；操作时仍须明确本次使用的角色。

### 2.3 其他计划类型

Y/XN/DC/FC/JD/TM 分别读取流程配置，不把 Y 链矩阵直接复制到所有类型。

- XN 跳过区域，通知链为客户→省区→大区→品类。
- XN 正向状态为 0→2→3→4→5→10，不产生 1、7。
- XN 省区退回客户时，客户和省区可见状态 6；省区有角色权限时可再次确认。
- 本次不因“拥有区域角色”自动扩大 XN 单据的区域可见范围。
- 某角色未配置在该审批链，但用户通过已有授权范围能看到单据且拥有该角色时，可以记录该角色确认；该结果不替代必需节点，不提供该角色的退回动作。
- DC/FC/JD/TM 的实际节点以有效数据库配置为准，未核对前不在本文臆定完整链。

## 三、审批权限

### 3.1 判断公式

```text
能审批 = 能看到单据
       AND 拥有本次使用的审批角色（含对应组织授权）
       AND 当前版本有效且未删除
       AND status IN (1, 2, 3, 4, 6, 7, 8, 9)
```

### 3.2 状态限制

| 状态 | 审批规则 |
|---|---|
| 0 | 未提交，不允许审批 |
| 1～4 | 允许按角色审批，不要求匹配当前通知节点 |
| 6～9 | 允许按角色审批，不要求本人是退回目标；仍受可见性限制 |
| 5 | 审批完成待回写，只读，不允许审批或保存调整 |
| 10 | 回写完成，只读，不允许审批或保存调整 |
| 历史、删除、无效版本 | 不允许写入 |

审批不设日期窗口。客户提报和客户重提按提报窗口规则校验；审批人员重审不套用提报窗口。

### 3.3 操作角色

- 单角色用户使用其已授权角色；多角色用户必须明确本次使用哪个角色，可以由工作台当前角色选择表达。
- 请求、服务端校验、确认字段和日志必须使用同一个操作角色。
- 一次操作只代表一个角色，不能默认一次通过所有角色。
- 不得从 `status`、通知接收人或组织层级推测操作角色。
- 收到通知但没有角色权限，不能审批；没有通知但满足上述条件，可以审批。

## 四、通知与列表

| 列表 | 含义 |
|---|---|
| 待我处理 | 流程当前通知我的单据 |
| 可审批 | 我能看到且有角色权限操作的未完成单据 |
| 已完成 | 5、10，只读 |

待我处理和可审批可以重叠。“待我处理”中的通知本身不授予权限。

| 操作 | 通知处理 |
|---|---|
| 当前通知角色通过 | 记录结果，沿配置寻找下一个未有效通过的节点并通知 |
| 非当前通知角色提前通过或再次确认，数据未变化 | 记录该角色结果，保持当前通知位置 |
| 流程到达已提前通过的节点 | 结果有效则跳过通知；失效则通知重审 |
| 审批依据变化 | 作废受影响结果，重新定位最早需要处理的节点并通知 |
| 退回 | 原待处理通知失效，通知退回目标 |

当可见性允许用户提前确认时，可以提前记录结果；本次不为了支持提前审批而扩大可见范围。

## 五、审批结果与数据有效性

审批通过只针对当时确认的数据有效。确认数据和“该审批是否仍有效”分开记录；保留字段不等于保留有效审批。

| 数据变化 | 结果处理 |
|---|---|
| 客户修改提报数量、金额、追加、追减 | 作废依赖这些数据的各级审批结果 |
| 某审批角色修改自己的确认数据 | 本次通过时记录该角色新结果；作废依赖这些数据的后续角色审批结果 |
| 只保存调整，尚未点击通过 | 保存数据，不自动产生通过结果；原结果如已不匹配新数据则失效 |
| 重复确认且依据未变化 | 不作废其他角色结果 |
| 查看或修改不影响审批依据的备注 | 不作废审批结果 |

失效审批保留日志，记录失效原因及关联的数据变更，不删除原审批历史。提前审批和正常审批使用相同有效性规则。

## 六、退回与重提

### 6.1 退回规则

满足审批权限的角色可以退回，不要求其为当前通知角色。

1. 按“计划类型 + 操作角色”定位配置链节点，退给该节点的前一个节点。
2. 不允许跨级退回。角色不在该链中时，没有配置退回目标，不提供退回操作。
3. 必须填写退回原因，记录操作人、操作角色和退回目标。
4. 作废发起退回角色及其后续角色的审批结果。
5. 清空发起退回角色自己的数量、金额、追加、追减四类确认字段，其余角色字段保留。
6. 客户提报端值不因退回清空。
7. 更新当前有效版本的退回状态，保证退回接收人能在有效版本查询中找到单据；同时保留历史和日志。
8. 状态变更、结果失效、字段清空和审批日志在同一事务内完成，提交后更新通知。

### 6.2 退回目标与状态码

退回码 = 配置链中退回目标的 DMS 节点码 + 6。

| 退回目标 | 退回码 |
|---|---|
| 客户 | 6 |
| 区域 | 7 |
| 省区 | 8 |
| 大区 | 9 |

例如 Y 省区退回→区域（7）；XN 省区退回→客户（6）。**清空字段按发起角色确定，不能由退回码硬编码推断发起方。** XN 的 6 应清省区字段，不能清区域字段。

### 6.3 重提

重提从退回目标在实际配置链中的下一个节点继续，再跳过已有有效审批的节点。

- Y：客户从 6 重提→区域（1）；区域从 7 重提→省区（2）。
- XN：客户从 6 重提→省区（2）。
- **废止“退回码 − 5”为通用公式**，只按配置链计算。
- 如重提生成新版本，旧版本保留留痕，新版本成为唯一有效版本；节点审批结果不得未经依据核对直接复制为有效通过。
- 原 V1.2 新版本节点确认字段一律 NULL 的规则继续适用于新建版本；“其他节点字段保留”指退回动作对当时版本的处理。

## 七、终审与 DMS 回写

进入 `status=5` 必须同时满足：

1. 客户已提交，且该次提交未因客户待修改重提而失效。
2. 配置链所有必需审批角色，都对当前审批依据有效通过。
3. 没有未处理的退回或失效结果。

品类提前通过不能单独触发回写；不在该链中的附加角色确认不替代必需节点。

- 只处理 `status=5` 的条目。
- 回写成功置 `status=10`、`sync_status=SYNCED`，记录 `finished_at`。
- 失败保持 5，`sync_status=FAILED`，按原幂等规则重试。
- 不引入 11；M、Z 使用同一终审和回写触发规则。
- `PLANE_NUM=plan_id` 等回写字段沿用 V1.2。

## 八、状态、通知位置和角色结果分开

### 8.1 状态码

| status | 业务阶段／显示名称 |
|---|---|
| 0 | 待提交 |
| 1 | 待区域处理 |
| 2 | 待省区处理 |
| 3 | 待大区处理 |
| 4 | 待品类处理 |
| 5 | 审批完成，待回写 |
| 6 | 退回销售 |
| 7 | 退回区域 |
| 8 | 退回省区 |
| 9 | 退回大区 |
| 10 | 回写完成 |

1～4 按实际配置链解释其通知阶段，未配置节点不产生相应正常状态。**不再仅凭状态码声称某角色已审批。** 原名称“区域已审批”等如用于历史展示，应明确为旧口径。

### 8.2 分开存储的业务信息

| 信息 | 用途 |
|---|---|
| 单据状态 | 当前业务阶段、退回状态、回写状态 |
| 通知位置 | 当前需要提醒的配置链节点 |
| 各角色审批结果 | 操作角色、通过/失效、所依据的数据版本或快照、时间 |
| 审批日志 | 操作人、操作角色、动作、变更前后状态、原因、失效记录、请求标识 |

`approval_level` 若保留表示配置链位置，必须与角色节点码分开。不得再要求它在所有计划类型上与 `status` 完全同值；XN 第一个审批位置对应省区节点码 2。

## 九、保持不变的基础规则

- 计划类型唯一来源为客户主数据，判定后写入 `plan_type_code`，后续不重复猜测。
- 合作方式 5→DC，6→FC，9→XN，1→Y；3 为直管分支：分类 kajxs→Y，否则客户组 H5→JD、J4→TM，其余→Y；其他及空值兜底 Y。
- 字符串精确比较，保留空值双保险。
- 流程配置来源 `hive.ods_dms.plan_workflow_config`，有效过滤 `status='1' AND delete_status='1'`；GEA 同步表按实际环境映射。
- 提报窗口读 `plan_window_config`，不写死日期；多组织命中取 REGION > PROVINCE > AREA > BASE。
- M 不使用追加/追减字段；Z 沿用原绝对净调整数据契约；金额与数量一致处理。

## 十、开发改造与验收

### 10.1 工作台／插件

- 保留组织、版本和可见状态筛选。
- 取消“通知任务授予审批权限”和“操作角色必须等于当前节点”的判断。
- 多角色操作明确角色；调整默认值、确认字段、请求和回读按该角色计算。
- 0、5、10 及历史版本写入口关闭，不能保留原状态 10 SAVE 特例。
- 分开展示待我处理与可审批，通知读取失败不能撤销已具备的角色权限。
- 展示有效审批结果，不再通过状态大小推断所有下级已审。

### 10.2 GEA 服务端

- 写接口重新核对可见范围、角色组织授权、有效版本和当前状态，不依赖通知候选人授权。
- 明确操作角色；对角色伪造、跨组织、旧快照和并发冲突进行校验。
- 持久化角色审批结果及依据，执行失效传播、角色退回和通知更新。
- 事务校验全部必需节点有效通过后才写 5，并保留幂等回写。
- 工作台不能通过本地伪造成功回执替代服务端实现；插件单独更新不代表后端规则已经生效。

### 10.3 核心验收场景

| 场景 | 预期 |
|---|---|
| Y 状态 2，区域可见并拥有区域角色，未收到通知 | 可以按区域角色审批，数据未变时不推进省区通知 |
| 有通知，无审批角色 | 不可审批 |
| 有角色，但不在可见组织范围 | 不可查看及审批 |
| 多角色用户操作 | 请求只携带本次明确角色，日志不代签其他角色 |
| Y 状态 7，省区再次确认 | 可审批；区域待处理未完成时不绕过该待处理事项 |
| 0、5、10、历史或已删除版本 | 界面和接口均拒绝写入 |
| 提前通过后，下级改变审批依据 | 受影响审批失效并重新通知 |
| 重复确认且依据不变 | 其他有效结果保留 |
| XN 省区退回 | 状态 6，清省区字段，通知客户；客户重提进入 2 |
| 非当前通知角色退回 | 按操作角色前一配置节点退回，原通知失效 |
| 品类通过，但必需节点尚未全部有效通过 | 不进入 5，不回写 |
| 必需节点全部有效通过 | 进入 5；回写成功进入 10，失败保持 5 |

## 十一、相对 V1.2 的废止项

| 旧规则 | 新规则 |
|---|---|
| 当前节点或通知候选人决定审批权 | 可见范围与审批角色决定权限 |
| 我之后的推进状态、我发起的退回一律只读 | 可见且有角色时允许审批；0、5、10 和历史版本仍不可写 |
| 一个 status 足以表示所有角色已审情况 | 状态、通知位置、各角色结果分开 |
| 每次通过固定推进一级 | 记录角色结果；通知按有效结果推进或保持 |
| 品类通过即表示全链通过 | 所有必需节点有效通过才完成 |
| 重提固定等于退回码减 5 | 按实际配置链续走 |
| status=10 可独立 SAVE | 10 终态只读 |
| 审批级别始终等于状态码 | 配置链位置与节点码分开 |
